herdr-tab-new

A shell helper — run from a plain terminal in Zed, with no arguments in the common case — that finds the existing herdr workspace matching the current project, creates a new named tab in it, and starts a fresh Claude session there, ready to begin new work.

TypeScript Bun yaml git herdr CLI herdr-spreader macOS compiled binary in ~/.local/bin

What the app does

  • Knows where it is

    Works out the project root from Zed's environment, falling back to the git root and then the current directory.

  • Finds the right workspace

    Matches that project against the live herdr workspaces and picks the one that belongs to it.

  • Creates a named tab

    Adds a new, focused tab to that workspace, named after the branch with a counter when names repeat.

  • Starts a fresh agent session

    Launches Claude in the new tab and waits until it is genuinely ready for input. Other agent kinds are available on request.

  • Optional isolated worktree

    On request, gives the new session its own git worktree and branch so it cannot collide with your working tree.

  • Brings a workspace up if needed

    If no live workspace matches, it asks herdr-spreader to build one from your declared layout — and stops clearly if there isn't one.

  • Remembers what it made

    Keeps a per-session record of every tab and worktree it created, and can list them back to you.

  • Cleans up after itself

    Closes the tabs it created and removes the worktrees it made, never touching anything you made by hand.

  • Shows its work first

    A dry-run mode prints the workspace, tab name and directory it would use, without creating anything.

  • Fails out loud

    Says exactly what was wrong — herdr not running, no matching workspace, agent never became ready — rather than half-creating something.

Already provided by the existing herdr setup

  • herdr 0.8.0 with a local socket API
  • Workspace, tab, pane and agent commands
  • Pane working directories, exposed per workspace
  • Built-in agent readiness detection for 20+ agent kinds
  • Named sessions, each with its own socket
  • herdr-spreader, with declared workspace layouts
  • artisann.zed-herdr, syncing herdr focus out to Zed
  • Zed setting the project root in its terminal environment
  • ~/.local/bin already on PATH

Out of scope (v1)

  • Inventing a workspace from nothing — a workspace is either already live, or declared as a herdr-spreader layout. Anything else is a hard failure, not a guess.
  • Firing automatically — spawning a session without being asked is wanted later, once zero-argument behaviour has proved itself.
  • Seeding an opening prompt — the new session opens bare. A wrong auto-written brief is worse than no brief.
  • Zed-specific behaviour — Zed only supplies the project root. The helper behaves identically in a Zed terminal, iTerm, or a shell an agent is driving.
  • Remote herdr sessions over SSH — local sockets only, including named local sessions.
  • Linux and Windows support — macOS is the only environment this needs to work in.
  • A configuration file — arguments and environment variables are enough at this size. Config is a thing to maintain.
  • Spawning several tabs in one run — one invocation creates one tab. Run it twice.
  • A Zed extension or MCP tool — a script on PATH works from every shell; an extension only works inside Zed.
  • Managing tabs it did not create — teardown is limited to its own records, so a stray run can never close your work.

Data model

What the helper needs to remember. Records are kept per herdr session, alongside that session's own files, so the default session and a named session never share state.

Spawned tab

sessionWhich herdr session this tab belongs to.
workspaceThe workspace the tab was created in, and its label at the time.
tabThe tab herdr gave back, so teardown can close exactly that one.
labelThe name shown in the tab bar, so you can refer to it by name.
directoryWhere the session was started — the project, or a worktree of it.
agent kindWhich agent was started in it — Claude unless told otherwise.
worktreeThe worktree and branch the helper created, when it created one. Empty otherwise — and only a worktree recorded here is ever removed.
createdWhen it was spawned, so the list reads newest-first and stale entries are obvious.

Related to · nothing else — this is the only thing the helper stores.

Prior art considered

The herdr ecosystem was checked before committing to this build, and the implementation language was reconsidered during milestone 1. Nothing found does the whole job — nothing creates a tab in an existing workspace and starts an agent in it from an outside terminal — but several things overlap, and the decision was taken deliberately to build anyway.

  • herdr’s own worktree commands — herdr can already create, open and remove a git worktree, with a branch, base, path and label. It produces a worktree-backed workspace, not a tab inside an existing one, so it does not fit this helper’s shape. The milestone-4 agent should still read its behaviour before designing worktree mode, and may call it rather than reimplement it.
  • herdr-plugin-workspace-manager — reacts to worktree and workspace events, applies a declarative layout, and starts agents waiting for readiness. It is not installed, and it hangs off workspace-level events, so it never fires for a new tab. Deliberately not a dependency.
  • Tab auto-naming plugins — plugins exist that rename tabs from the agent’s own conversation. If one is ever installed it will overwrite the name this helper sets. The generated name must therefore be a good starting point, not something later behaviour depends on.
  • Building this as a herdr plugin — ruled out. herdr runs plugin commands with the plugin’s own directory as their working directory and supplies its own workspace context; the calling shell’s directory is never consulted, and an invocation takes no arguments. A plugin would therefore answer “which workspace is herdr showing?” when the question is “which project is open in Zed?”. Both comparable projects ship a plugin and a standalone CLI for the same reason. A plugin wrapper remains the right home for the parked auto-fire feature, invoking this same binary.
  • Plain herdr configuration — a keybinding already creates a named tab inheriting the current directory, but no configuration option starts an agent in it. Custom command bindings run detached, in a temporary pane, or in a popup, and none of them create a tab. Configuration can bind a key to this helper; it cannot replace it.

Milestones

1

Resolve and dry run

Everything that happens before anything is created. The helper works out where it is, which herdr session and workspace it is talking to, and what the new tab would be called — then prints that plan without touching a thing.

What gets built

  • The herdr-tab-new command itself, with help text
  • Project root worked out from Zed's environment, then the git root, then the current directory
  • The correct herdr session picked up, including named sessions
  • The matching live workspace identified from the project directory
  • A tab name generated from the branch, with a counter when that name is already taken
  • A dry-run mode printing the session, workspace, tab name and directory it would use
  • Distinct, readable failures for herdr missing, herdr not running, and no matching workspace — the last one saying whether a spreader layout exists for the project
  • Installed into ~/.local/bin so it runs from anywhere

Not in this milestone

  • Creating a tab, or anything else that changes herdr's state
  • Starting an agent
  • Calling herdr-spreader — this milestone only reports that a layout exists
  • Any stored records, worktrees, teardown, or choosing a different agent kind

Done when: running the dry run inside a project that has a live herdr workspace prints the workspace it would use and the tab name it would create — and running it somewhere with no matching workspace stops with a message that says exactly that, having changed nothing.

2

Create and start

The helper stops describing and starts doing. This is the milestone that makes it genuinely useful: one command and you are sitting in a fresh Claude session in the right place.

What gets built

  • A new tab created in the resolved workspace, opened in the project directory and given focus
  • Claude started in that tab, with the command waiting until it is actually ready for input before returning
  • An optional name argument overriding the generated tab name
  • When no live workspace matches, herdr-spreader is asked to bring the declared layout up, then resolution is retried
  • A hard stop, with a clear message, when the project has no declared layout to fall back on
  • A short confirmation of what was created, and a clear report if the agent never came up

Not in this milestone

  • Any agent other than Claude
  • Recording what was created
  • Worktrees and teardown
  • Sending an opening prompt into the new session

Done when: running the command with no arguments from a project's terminal in Zed leaves you looking at a new, correctly named, focused tab in the right herdr workspace, with Claude running in the project directory and ready to be typed into.

3

Agent kinds and records

Claude stops being the only option, and the helper starts remembering what it has done — which is what makes cleanup possible later.

What gets built

  • A way to choose the agent, defaulting to Claude
  • An unsupported agent name rejected before anything is created, listing what is supported
  • A per-session record written for every tab the helper creates
  • A listing of the tabs it created for the current session, newest first, marking any that no longer exist
  • Two runs at once never losing each other's records

Not in this milestone

  • Acting on the records — nothing is closed or removed yet
  • Worktrees
  • A configuration file for setting a default agent
  • Listing across all sessions at once

Done when: asking for a different agent starts that agent instead of Claude, asking for one that does not exist fails immediately without creating a tab, and the listing shows every tab the helper has created in this session.

4

Worktree mode

On request, the new session gets its own copy of the project on its own branch, so an agent working in it cannot disturb what you have open.

What gets built

  • An opt-in worktree mode, taking a branch name or working one out from the tab name
  • The new tab opening in the worktree rather than the main checkout, with a name that makes the branch obvious
  • Both new and existing branches supported
  • The worktree and branch recorded, so later cleanup knows the helper made them
  • Clear refusals when the project is not a git repository, the branch is already checked out elsewhere, or the location is taken — refusing before any tab is created

Not in this milestone

  • Removing worktrees
  • Worktrees by default
  • Copying ignored files such as local environment files or dependencies into the worktree
  • Anything to do with pushing, pull requests, or merging

Done when: asking for a worktree creates one on the named branch, opens a focused tab running Claude inside it, records both — and your original checkout is left exactly as it was.

5

Teardown

The other half of spawning. Finished sessions get cleared away — but only the ones the helper made, and only when it is safe to do so.

What gets built

  • A teardown command, taking a tab name or clearing everything the helper made in this session
  • Worktrees the helper created removed along with their tab
  • A worktree with uncommitted work left alone and reported, not deleted
  • A preview mode showing what teardown would close and remove
  • Records for tabs that are already gone quietly cleared away
  • A summary of what was closed, removed, and skipped

Not in this milestone

  • Closing tabs the helper did not create, whatever they are called
  • Closing whole workspaces
  • Deleting branches, or anything that could lose committed work
  • Automatic cleanup on a timer or on idle

Done when: after spawning several sessions, teardown closes exactly those tabs and removes their clean worktrees — leaving your hand-made tabs open, and any worktree with uncommitted changes untouched and reported.
